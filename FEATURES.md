# Features

What the app does now. Edit in place when a change alters what users see or can do.

## What it does

- `offer-engine check-env` lists each `.env` key as `set` or `missing`, never its value. It exits 1 when `OFFER_BOT_TOKEN`, `OFFER_BOT_USERNAME` or `ANTHROPIC_API_KEY` is missing or `CUSTOMER_BOTS` is malformed.
- `offer-engine setup` walks a developer through five steps: create the Offer Bot in BotFather, turn on Bot-to-Bot Communication Mode, create 6–8 Customer Bots, enter the Anthropic API key and model IDs, then check `.env`. It checks each bot token with Telegram `getMe`, reads tokens and the key hidden, never prints them, and saves `.env` with mode 0600 after each step. Running it again offers to keep each value already set.
- `offer-engine db init` creates the SQLite database at `DB_PATH` (default `data/offer_engine.db`) or applies new schema files. Running it again is safe.
- `offer-engine clock show` prints the simulated time, which starts at `2026-12-01 00:00`. `offer-engine clock advance --hours N` or `--days N [--seed S]` runs the marketplace forward one hour at a time and never moves back. Every generated Customer visits, views, carts, abandons, orders, gets deliveries and returns, and earns, burns or loses points, and the `customers` table's points follow. Orders placed in the last days of the history arrive on time. A Customer holding a sent or claimed Offer doesn't order organically that day. Queued Offers to Customers without a chat become `sent` at their send time. Every hour four Triggers run the decision pipeline: an abandoned cart, points expiring within `points_expiry_warning_days` (7), `long_gap_days` (45) since the last order, and a Customer's first delivery. Each underlying event (the cart, the expiry date, the last order, the first delivery) fires once, and the Rules still decide whether an Offer goes out. The command prints the new time and the counts (`sessions 3,165 · product_views 6,310 · … · orders 47 · … · decisions.cart_abandoned 168 · decisions.long_gap 32`). The same seed and starting state give the same events, and stopping mid-day changes nothing.
- Rule settings are versioned in the database. Version 0 is the defaults, and a revert saves a new version equal to the old one. There is no command or console page for this yet.
- `offer-engine start` runs the Offer Bot and the Customer Bot simulator together, prefixing each line of output with the process name. Ctrl-C stops both. If either exits with an error, both stop.
- Sending `/start` to the Offer Bot makes that chat the Tester for demo Customer `C00001` and sends a demo Offer Card: a PNG with "15% off Fashion", "Up to ₹300 off", the code `POE-DEMO01` and the expiry, plus a caption. `/claim POE-DEMO01` replies "Claimed POE-DEMO01. Show this code at checkout."
- `offer-engine demo-send` has the Offer Bot send the demo card to the first Customer Bot by `@username`. That bot replies `/claim POE-DEMO01`, and the Offer Bot acknowledges and logs the Claim.
- `offer-engine generate --customers N --months M --seed S` builds a fictional marketplace: 5 categories (margins 10–45%), 200 products in ₹, N Customers (IDs `C00001…` in signup order) and M months of events ending at the clock start (sessions, product views, carts, abandoned carts, orders, deliveries, returns and points). The history also holds random past Offers, as A/B tests would leave them. Customers outside the Holdout get one at 30% of moments (an abandoned cart, 45 days without an order, a Friday 18:00 broadcast), at most one per 7 days. Its type and depth are random. Ground Truth decides whether the Customer buys while the Offer is valid, and the order it places is linked to the Offer. 25% of the rest Claim without buying, a few dismiss it, and 1% opt out. It prints counts per table and per event kind. The same seed gives the same database. Each run deletes the old world first, including Offers, Decisions and chat links.
- `offer-engine eligible --demo` prints the Eligible Set for a built-in Customer under the default Rules, and `--customer ID` does the same for a generated Customer at the clock's time under the current Rules. It shows each allowed Offer Type with its parameter ranges and the Binding Rule for each limit, the send window, and the options dropped with the Rule that emptied them.
- `offer-engine trigger cart-abandoned CUSTOMER_ID` records an abandoned cart at the clock's time (the Customer's latest carted product, else the latest viewed one) and runs the decision pipeline. A second call for the same Customer at the same simulated time is refused. The Rules give the Eligible Set. For a chat-attached Customer, when `ANTHROPIC_API_KEY` is set, Claude (the model in `OFFER_AGENT_MODEL`) picks one option or No Offer, sets its parameters and featured products, and writes the caption and reason (`chooser=agent`). Every other Customer gets the rules chooser, which picks the option and parameters with the highest Lift × margin − expected cost, or No Offer if none is positive (`chooser=rules`). Validation re-checks the pick, Caption Check included. If the agent's pick fails, or the API errors or takes over 20 s, the rules chooser decides instead (`chooser=fallback`) and the Decision keeps the agent's raw answer and every failure. The command prints the Decision (`pct_category beauty pct=8 cap=70 · chooser=rules · binding: max_pct_by_loyalty_tier · rule v0 · valid`) and, for an Offer, its `POE-` code, send and expiry times, worst-case and expected cost, caption and reason. A Fallback Decision also shows the agent's rejected proposal and the Validation failures. The Offer is saved as `queued` and counts against the weekly budget at worst-case cost (or expected cost in that budget mode).
- `generate` also gives every Customer a hidden Ground Truth: a buying chance for each Offer Type that rises (or, for Sleeping Dogs, falls) with the Offer's depth, and a Response Class. Only the simulator reads it. `offer-engine ground-truth summary` prints the Response Class shares against calibration target 9, plus the mean base chance and max Lift per Offer Type.
- `offer-engine calibrate` measures the generated history against the calibration targets in `docs/research/ecommerce-benchmarks.md` and prints one row per figure: its target number, value, range and `ok`, `MISS` or `miss (category split)`. It covers conversion, the weekly buying chance, cart abandonment and recovery, Redemption per send, repeat rate, orders per year, lapse, margins, spend concentration, Response Classes, festive share, points breakage and opt-out. It reads only events before the clock start, so it still works after `clock advance`. `--strict` exits 1 when any figure other than a category split misses.
- `offer-engine history summary` prints the past Offers per Offer Type (sent, Claim and Redemption rates, the 7-day purchase rate, cost and margin per Redemption), then per moment the purchase rate with and without an Offer, and Redemption per send against calibration target 4.
- `offer-engine decisions --last N [--customer ID]` lists Decisions newest first with the Offer's terms, the chooser, the Binding Rule, the rule version and the Validation result.
- `offer-engine caption-check "TEXT" --offer-type T --param NAME=VALUE --category C` runs the Caption Check and prints `PASS` or one reason per line, exiting 1 on failure. It rejects numbers, ₹ amounts, percentages and multipliers that aren't the Offer's terms (digits, number words, Hinglish, emoji keycaps, Devanagari digits), deadlines ("tonight", "until Sunday", "in 6 hours", "kal tak"), invented urgency ("hurry", "only a few left"), promises the Offer doesn't make ("free gift", "cashback", free delivery on a non-shipping Offer), and captions over 280 characters or blank. Validation runs the same check on every proposed caption.

## Known limits

- Nothing sends Offers yet (T10); they stay `queued`. Advancing the clock creates organic events, fires the event Triggers and marks Offers sent, but nothing settles Offer outcomes (T18) or runs the Daily Sweep (T20) yet. Only `offer-engine trigger cart-abandoned` fires a Trigger by hand.
- The rules chooser uses fixed Lift guesses per Offer Type and can offer a different category from the abandoned cart. The agent sees those guesses too until Estimated Lift arrives with T16.
- No command links a Customer to a chat yet (`chats link` comes with T10), so the agent only decides for a Customer given a `chats` row by hand. The agent's own path hasn't been run against the real API yet; tests use a fake client.
- Live Offers aren't settled until T18; only past Offers in the history have outcomes. Past Offers are redeemed far more often than calibration targets 3 and 4 allow (about 15% of targeted sends against 1.5–5%), because every Customer reads every Offer and every buyer uses the code (docs/QnA.md Q41). Generating 10k Customers × 12 months takes about 80 seconds; one live day for them, Triggers included, takes about 5 s.
- The Caption Check accepts a caption that names the wrong category, and "today" or "this week" when not worded as a deadline.
- `setup` does not ask for `DB_PATH`, `SEED` or `CONSOLE_PASSWORD`. Edit `.env` by hand to set them.
- The bots send only the hard-coded demo Offer, and only the first Customer Bot in `CUSTOMER_BOTS` runs.
- The demo has no Claim / Not now / Stop buttons, and Claims are logged, not stored.
